## Objetivo
`POST /webhooks/payment` lee el body crudo, verifica la firma HMAC antes de parsear, valida el payload con zod, llama a `processWebhookEvent` y responde `200 { received: true, duplicate }`.

## Contexto
- Header de firma: `X-Provider-Signature: t=<unix>,v1=<hex>`. La verificación ya existe en `webhooks.signature.ts` (T3.5). Esta tarea solo la usa.
- `webhookEventSchema` ya existe en `webhooks.schemas.ts` (T3.6). No usa `.strict()`: descarta campos desconocidos sin fallar (AGENTS.md, design §8). Si el proveedor agrega un campo, un `400` provocaría reintentos infinitos de su lado.
- Esta es la única tarea de las fases 5 y 6 que edita `src/app.ts`. T6.1 solo edita `src/server.ts`. Así T5.x y T6.x no chocan.

## Pasos
1. `const raw = await c.req.text()`. Es la única lectura del body.
2. `verifySignature({ header: c.req.header("X-Provider-Signature"), rawBody: raw, secret: config.WEBHOOK_SECRET, toleranceS: config.WEBHOOK_TOLERANCE_S, now })`. Si falla, `throw new AppError("WEBHOOK_SIGNATURE_INVALID")`.
3. `JSON.parse(raw)` en un `try`. Si falla, `AppError("VALIDATION_ERROR")`.
4. `webhookEventSchema.safeParse(json)`. Si falla, `VALIDATION_ERROR` con `errors` traducidos con el mismo helper que T3.6 usa para el hook de `zValidator`. Al servicio se pasa `result.data`, que ya no trae los campos desconocidos.
5. `const { duplicate } = await webhooksService.processWebhookEvent(event, c.var.logger)`.
6. `return c.json({ received: true, duplicate }, 200)`.
7. En `createApp`, montar con `app.route("/webhooks", webhooksRoutes(deps))`.
8. Tests unitarios: firma válida, firma inválida, timestamp vencido, header ausente, JSON roto con firma válida, payload inválido con firma válida, payload con un campo desconocido y firma válida, y que el servicio no se llama en ninguno de los fallos.

## Restricciones
- La firma se verifica sobre el string exacto recibido. Nunca sobre `JSON.stringify(JSON.parse(raw))`.
- No usar `zValidator("json", ...)` en esta ruta: consume y parsea el body antes de la firma.
- La ruta no toca Prisma (AGENTS.md). Solo llama al servicio.
- Todos los errores salen por el error handler global como `application/problem+json`.
- `now` inyectable en las dependencias de la ruta para testear el timestamp sin esperar.

## Trampas conocidas
- **Parsear JSON antes de verificar la firma.** Gasta trabajo en payloads no firmados y abre la puerta a responder `400` a un atacante en vez de `401`. El orden es firma, parseo, schema (R9.2, R9.3).
- **Re-serializar el JSON para firmar.** Cambia espacios y orden de claves, y la firma legítima del proveedor deja de coincidir.
- **Usar `c.req.json()` y luego `c.req.text()`.** El body ya se consumió, o se obtiene otra representación. Leer una sola vez con `text()`.
- **Comparar la firma con `===`.** Eso es responsabilidad de T3.5, pero el revisor verifica que la ruta no haga una comparación propia.
- **Responder `200` con firma inválida "para que el proveedor no reintente".** El spec pide `401` (R9.2).
- **Leer `WEBHOOK_SECRET` de `process.env`.** Viene de `deps.config`.
- **Rechazar campos desconocidos con `400`.** El proveedor reintentaría para siempre un evento válido. Ni `.strict()` en el schema ni una validación propia en la ruta.

## Criterios de aceptación
- [ ] Firma válida y payload válido: `200 { "received": true, "duplicate": false }`.
- [ ] Servicio devuelve duplicado: `200 { "received": true, "duplicate": true }`.
- [ ] Firma inválida, header ausente o timestamp fuera de tolerancia: `401 WEBHOOK_SIGNATURE_INVALID` y el servicio no se llama.
- [ ] Firma válida con body que no es JSON: `400 VALIDATION_ERROR`.
- [ ] Firma válida con payload que no cumple el schema: `400 VALIDATION_ERROR` con `errors` no vacío.
- [ ] Firma válida con un campo desconocido extra: `200`, y el servicio recibe el evento sin ese campo.
- [ ] Todas las respuestas de error son `application/problem+json` con `request_id`.
- [ ] `grep -n "zValidator\|c.req.json" src/features/webhooks/webhooks.routes.ts` no encuentra nada.
