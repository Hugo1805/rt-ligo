## Objetivo
Probar contra Postgres y Redis reales que un webhook nunca acredita dos veces, que respeta el orden de llegada y que un error propio no lo marca como procesado.

## Contexto
- Los tests levantan dos instancias con `createApp`, cada una con su cliente Prisma y Redis, como pide AGENTS.md para concurrencia.
- Cada test crea su wallet y su operación con datos únicos (`userId` con `crypto.randomUUID()`), así no depende del seed ni de otros tests.
- El escenario R9.8 necesita un proveedor controlable: un `PaymentProvider` de test cuyo `charge` devuelve una promesa que el test resuelve a mano. La DB y Redis siguen siendo reales.
- Para el error transitorio se usa el `applyCredit` inyectable de `createWebhooksService` (T5.1).
- Cada evento procesado queda con un `outcome` de design §6 (`APPLIED`, `NOOP_ALREADY_APPLIED`, `IGNORED_OUT_OF_ORDER`, `ORPHAN`, `AMOUNT_MISMATCH`, `PENDING_NO_CHANGE`). Los escenarios lo verifican leyendo `WebhookEvent` con Prisma.
- `webhookEventSchema` descarta campos desconocidos sin fallar: un campo extra no da `400`.

## Pasos
1. Helper que arma un evento, lo serializa una vez, lo firma y lo envía con `app.request("/webhooks/payment", ...)`.
2. Escenarios:
   1. **Duplicado:** mismo `charge.succeeded` dos veces sobre una operación `UNKNOWN`. Primera `duplicate: false`, segunda `duplicate: true`. Un solo `LedgerEntry`, saldo incrementado una vez, `outcome = "APPLIED"`.
   2. **Duplicado concurrente:** el mismo evento enviado con `Promise.all` a `app1` y `app2`. Un solo asiento y un solo `WebhookEvent`.
   3. **`failed` tras `COMPLETED`:** operación completada, llega `charge.failed`. `200`, la operación sigue `COMPLETED`, saldo igual, `outcome = "IGNORED_OUT_OF_ORDER"`.
   4. **`succeeded` tras `FAILED`:** operación fallida, llega `charge.succeeded`. `200`, sigue `FAILED`, sin asiento, saldo igual, `outcome = "IGNORED_OUT_OF_ORDER"`, log `webhook.anomaly` nivel `error`.
   5. **Webhook antes de la respuesta síncrona (R9.8):** `POST /cash-in` en `app1` con el proveedor bloqueado. Mientras espera, `charge.succeeded` llega a `app2`. Luego se libera el `charge`. La respuesta síncrona es `200 completed` con el `new_balance` del asiento, y hay un solo asiento.
   6. **Monto distinto:** evento con `amount` distinto al de la operación. `200`, sin asiento, operación sin cambio, `outcome = "AMOUNT_MISMATCH"`.
   7. **Moneda distinta:** igual que el anterior con `currency` distinta. Si `webhookEventSchema` solo acepta `PEN`, documentar que este caso lo cubre la validación y omitirlo.
   8. **Error transitorio:** `applyCredit` inyectado que lanza en la primera llamada. Respuesta `5xx` y no existe `WebhookEvent` con ese `event_id`. Se reenvía el mismo evento con el `applyCredit` real: `200 duplicate: false`, operación `COMPLETED`, un asiento.
   9. **Firma inválida:** `401 WEBHOOK_SIGNATURE_INVALID`, ningún `WebhookEvent` creado.
   10. **Huérfano:** `reference` inexistente. `200`, `WebhookEvent` guardado con `operationId: null` y `outcome = "ORPHAN"`.
   11. **Campo desconocido:** `charge.succeeded` firmado sobre una operación `UNKNOWN` con un campo extra en la raíz y en `data`. `200 duplicate: false`, operación `COMPLETED`, un asiento. No es `400`.
3. `afterAll`: `$disconnect` de cada Prisma y `quit` de cada Redis.

## Restricciones
- Postgres y Redis reales. Prohibido un repositorio en memoria para estos escenarios.
- Cada instancia tiene su propio `PrismaClient` y su propio cliente Redis.
- Importar solo desde `bun:test`.
- Aserciones sobre la DB con el cliente Prisma: contar `LedgerEntry` por `operationId` y leer `Wallet.balance`.
- Comparar saldos con `Prisma.Decimal.equals`, no con `number`.

## Trampas conocidas
- **Firmar un body y enviar otro.** Si el test hace `JSON.stringify` dos veces, puede cambiar el orden y la firma falla por motivos ajenos al test. Serializar una sola vez.
- **Probar "concurrencia" con dos requests a la misma instancia.** No prueba nada entre pods. Usar `app1` y `app2`.
- **Usar `setTimeout` para ordenar el escenario R9.8.** Es frágil. Usar una promesa diferida que el test controla.
- **Afirmar solo el status HTTP.** El valor está en la DB: número de asientos, saldo y estado de la operación.
- **Simular el error transitorio con un `P1001` real.** `withDbRetry` lo reintenta en el mismo request y el test termina en `200`. Para R9.10 el error debe agotar el request, por eso se usa un error no reintentable inyectado.
- **Reusar `event_id` o `userId` fijos entre tests.** El segundo run falla por `P2002` de una corrida anterior.

## Criterios de aceptación
- [x] Los 11 escenarios existen y pasan.
- [x] Cada escenario que procesa un evento verifica su `outcome` en `WebhookEvent`.
- [x] Un payload firmado con un campo desconocido responde `200`, no `400`.
