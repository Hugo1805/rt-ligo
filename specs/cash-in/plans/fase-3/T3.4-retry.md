## Objetivo
`retry(fn, options)` ejecuta una función async y la reintenta solo cuando un predicado `shouldRetry` lo permite, con backoff `min(cap, base * 2^n)` y full jitter. El azar y la espera son inyectables para tests deterministas.

## Contexto
Lo usan dos llamadores que llegan después:
- T4.6, hacia el proveedor: reintenta errores técnicos con la misma referencia, nunca un `declined` ni un timeout.
- T4.4, `withDbRetry`: reintenta errores transitorios de Prisma.
Este módulo no conoce a ninguno de los dos. La decisión de qué es reintentable la toma el predicado que pasa el llamador.
Valores por defecto de design §7: base 100 ms, cap 1000 ms. El número de reintentos lo pasa siempre el llamador, porque viene de config (`PROVIDER_MAX_RETRIES`) o de T4.4.

## Pasos
1. `RetryOptions`:
   - `maxRetries: number`. Reintentos además del primer intento. `maxRetries: 2` significa hasta 3 llamadas.
   - `shouldRetry: (error: unknown, attempt: number) => boolean`. Obligatorio, sin default.
   - `baseMs?: number`, default 100. `capMs?: number`, default 1000.
   - `random?: () => number`, default `Math.random`. Devuelve un valor en `[0, 1)`.
   - `sleep?: (ms: number) => Promise<void>`, default con `setTimeout` o `Bun.sleep`.
   - `onRetry?: (info: { attempt: number; delayMs: number; error: unknown }) => void`, para que el llamador loguee con su propio logger.
2. `computeBackoffMs(retryIndex, { baseMs, capMs, random })`: `Math.floor(random() * Math.min(capMs, baseMs * 2 ** retryIndex))`. `retryIndex` empieza en 0 para el primer reintento.
3. `retry(fn, options)`:
   1. Llama `fn(attempt)`, con `attempt` empezando en 0.
   2. Si resuelve, devuelve el valor.
   3. Si lanza y quedan reintentos y `shouldRetry(error, attempt)` es `true`, calcula la espera, llama `onRetry`, espera con `sleep` y vuelve a 1.
   4. Si no, relanza el mismo error, sin envolverlo.
4. Validar opciones: `maxRetries` entero `>= 0`, `baseMs` y `capMs` positivos. Si no, lanzar `TypeError` antes de llamar a `fn`.
5. Tests con `random` y `sleep` falsos que registran las esperas:
   - Éxito al primer intento: una llamada, cero esperas.
   - Falla dos veces y luego tiene éxito con `maxRetries: 2`: tres llamadas y devuelve el valor.
   - Falla siempre con `maxRetries: 2`: tres llamadas y relanza el último error, misma instancia.
   - `shouldRetry` devuelve `false`: una sola llamada y relanza.
   - Con `random = () => 0.999`, las esperas son `99, 199, 399, 799, 999, 999` para base 100 y cap 1000. Con `random = () => 0`, todas son `0`.
   - `fn` recibe el número de intento.
   - `maxRetries: -1` lanza `TypeError` sin llamar a `fn`.

## Restricciones
- Sin dependencias nuevas.
- Sin logger dentro de `retry`. El llamador loguea con `onRetry`.
- Sin estado de módulo: cada llamada es independiente.
- `shared/` no importa de `features/` ni conoce errores de Prisma o del proveedor.

## Trampas conocidas
- El agente tiende a reintentar cualquier error por defecto. Eso reintentaría un `declined` del proveedor (R6.2) o un timeout que debe quedar `UNKNOWN` (design §7). `shouldRetry` es obligatorio y sin default.
- El agente tiende a confundir intentos con reintentos. Design dice "máximo 2 reintentos" para el proveedor: son 3 llamadas. Un test lo fija.
- El agente tiende a escribir `base * 2 ** n + random() * base`, que es jitter aditivo, no full jitter. Full jitter es `random() * min(cap, base * 2^n)`.
- El agente tiende a aplicar el `cap` después del jitter o a olvidarlo, y con `n` grande la espera crece sin tope.
- El agente tiende a usar `setTimeout` real en los tests, que los hace lentos y frágiles. Se inyecta `sleep`.
- El agente tiende a envolver el error final en uno nuevo, por ejemplo `new Error("max retries")`. El llamador necesita la instancia original para distinguir un timeout de un error técnico.
- El agente tiende a esperar también después del último intento fallido. No se espera si no habrá otro intento.

## Criterios de aceptación
- [ ] `retry` sin `shouldRetry` no compila: un test lo fija con `// @ts-expect-error`.
- [ ] Con `maxRetries: 2` y fallas continuas, `fn` se llama exactamente 3 veces.
- [ ] El error relanzado es la misma instancia que lanzó `fn`.
- [ ] Las esperas siguen `random() * min(cap, base * 2^n)`, verificado con `random` fijo.
- [ ] No hay espera después del último intento.
- [ ] Los tests no usan temporizadores reales.
- [ ] `bun run test:unit` y `bun run typecheck` pasan.
