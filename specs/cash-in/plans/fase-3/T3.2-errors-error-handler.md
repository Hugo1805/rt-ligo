## Objetivo
`AppError` con el catálogo de códigos de design §9, y un error handler global de Hono que convierte cualquier error en `application/problem+json` (RFC 9457), con `request_id` y sin filtrar detalles internos.

## Contexto
El middleware de correlation de T2.5 deja `c.var.requestId` y `c.var.logger` en el contexto, y exporta el tipo de variables de Hono. El handler los usa.
T2.6 deja en `createApp` un `onError` mínimo y corre en paralelo con esta tarea. Para no tocar el mismo archivo, este plan no modifica `src/app.ts`: entrega `errorHandler` probado con una app Hono propia del test. Conectarlo con `app.onError(errorHandler)` queda fuera de alcance.
El hook de zod de T3.6 lanza `AppError` con `VALIDATION_ERROR` o `IDEMPOTENCY_KEY_*`. Para un body que no es JSON, Hono lanza su propio `HTTPException(400)` antes de que corra el hook; design §9 fija que sale como `VALIDATION_ERROR`.
Una ruta inexistente sale como `NOT_FOUND` (design §9). Hono la atiende con `app.notFound`, no con `onError`, por eso este plan exporta además un `notFoundHandler`.

## Pasos
1. `ERROR_CATALOG` como objeto `as const` con los 12 códigos de design §9, incluido `NOT_FOUND` (404, `retryable: false`). Cada entrada: `status`, `title`, `retryable` y, cuando aplica, `retryAfterS`:
   - `OPERATION_IN_PROGRESS`: `retryAfterS: 1`.
   - `SERVICE_UNAVAILABLE`: `retryAfterS: 2`.
2. `type ErrorCode = keyof typeof ERROR_CATALOG`.
3. `class AppError extends Error` con `code`, `status`, `retryable`, `detail`, `operationId?`, `errors: FieldError[]` y `cause?`. Constructor `new AppError(code, { detail?, operationId?, errors?, cause? })`. `status` y `retryable` salen siempre del catálogo, nunca del llamador.
4. `type FieldError = { field: string; message: string }`.
5. `toProblem` arma el cuerpo con `type`, `title`, `status`, `code`, `detail`, `request_id`, `retryable`, `errors` y `operation_id` solo si existe. `type` es `https://errors.ligo.pe/cash-in/<code-en-kebab>`: `IDEMPOTENCY_KEY_REUSED` da `idempotency-key-reused`.
6. `errorHandler(err, c)`:
   - `AppError`: usa su código.
   - `HTTPException` de Hono con status `400`: `VALIDATION_ERROR` con un `detail` genérico, por ejemplo "El body no es JSON válido.". No copiar `err.message`.
   - Cualquier otro error, incluidos los de Prisma y del proveedor: `INTERNAL_ERROR`.
   - Responde con `c.json(body, status)` y fuerza `Content-Type: application/problem+json`.
   - Agrega `Retry-After` cuando el código tiene `retryAfterS`.
   - Loguea con `c.var.logger`: `warn` para errores 4xx, `error` con `err` y stack para 5xx. El stack va solo al log.
   - Si `c.var.requestId` no existe, porque el error ocurrió antes del middleware, usa el header `X-Request-Id` de la respuesta o genera uno.
7. `notFoundHandler(c)` responde con `toProblem` el código `NOT_FOUND`, con el mismo `Content-Type`, `request_id` y forma que `errorHandler`.
8. Tests:
   - Cada código del catálogo produce el status, `title`, `retryable` y `type` esperados.
   - Una ruta que lanza `new AppError("PAYMENT_DECLINED", { operationId: "op_1" })` responde `422`, `Content-Type: application/problem+json`, `operation_id: "op_1"`, `errors: []` y el mismo `request_id` que el header `X-Request-Id`.
   - `OPERATION_IN_PROGRESS` lleva `Retry-After: 1`; `SERVICE_UNAVAILABLE` lleva `Retry-After: 2`.
   - Una ruta que lanza `new Error("connect ECONNREFUSED 10.0.0.5:5432")` responde `500 INTERNAL_ERROR` y el body no contiene `ECONNREFUSED`, `10.0.0.5` ni `stack`.
   - Un `HTTPException(400, { message: "Malformed JSON in request body" })` responde `400 VALIDATION_ERROR` sin ese mensaje.
   - `VALIDATION_ERROR` con `errors` los devuelve tal cual.
   - Una app de test con `app.notFound(notFoundHandler)` responde a una ruta inexistente `404 NOT_FOUND` en `application/problem+json`, con `errors: []` y el `request_id` del header.

## Restricciones
- No agregar códigos fuera de design §9. Si falta uno, detenerse y proponerlo en el spec.
- `shared/` no importa de `features/`.
- No tocar `src/app.ts`: lo está modificando T2.6 en paralelo.
- Ninguna ruta arma JSON de error a mano: todo pasa por `errorHandler`.
- El `detail` de `INTERNAL_ERROR` es un texto fijo.

## Trampas conocidas
- El agente tiende a poner `detail: err.message` para errores desconocidos. Eso filtra mensajes de Prisma con nombres de tablas, constraints o el host de la DB, prohibido por R12.3.
- El agente tiende a incluir `stack` en el body cuando `NODE_ENV` no es `production`. Prohibido en cualquier entorno.
- El agente tiende a usar `c.json()` y olvidar que pone `application/json`. El `Content-Type` debe ser `application/problem+json`; se verifica en el test.
- El agente tiende a dejar que `HTTPException` de Hono salga con su propia respuesta de texto plano llamando `err.getResponse()`. Un body no JSON debe salir como problem+json `VALIDATION_ERROR`.
- El agente tiende a permitir `new AppError(code, { status })` para sobrescribir el status. El status es siempre el del catálogo.
- El agente tiende a omitir `errors` cuando está vacío. El contrato pide `errors: []`.
- El agente tiende a poner `operation_id: null` cuando no hay operación. Se omite la propiedad.
- El agente tiende a inventar códigos como `BAD_REQUEST` o `METHOD_NOT_ALLOWED` para casos sin entrada en el catálogo.
- El agente tiende a dejar la ruta inexistente con el `404 Not Found` en texto plano por defecto de Hono. Sale como `NOT_FOUND` en problem+json desde `notFoundHandler`.
- El agente tiende a mapear el `AppError` a HTTP en cada ruta con `try/catch`. Las rutas lanzan y el handler responde.

## Criterios de aceptación
- [x] El catálogo tiene exactamente los 12 códigos de design §9 con su status, `retryable` y `Retry-After`.
- [x] Toda respuesta de error tiene `Content-Type: application/problem+json`.
- [x] El body tiene `type`, `title`, `status`, `code`, `detail`, `request_id`, `retryable` y `errors`, y `operation_id` solo cuando existe.
- [x] `request_id` del body coincide con el header `X-Request-Id`.
- [x] Un error desconocido responde `500 INTERNAL_ERROR` sin mensaje ni stack original.
- [x] Un `HTTPException(400)` responde `400 VALIDATION_ERROR`.
- [x] `notFoundHandler` responde `404 NOT_FOUND` en problem+json.
- [x] El stack de un 5xx aparece en el log y no en la respuesta.
- [x] `bun run test:unit` y `bun run typecheck` pasan.
