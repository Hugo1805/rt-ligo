## Objetivo
Schemas zod de `POST /cash-in` (header y body) y del evento de webhook, con sus tipos derivados, más los hooks de `@hono/zod-validator` que convierten un fallo en `AppError`. Ninguna ruta arma un error de validación a mano.

## Contexto
- API de zod 4: `z.uuid()`, `z.iso.datetime()`, parámetro `error` en lugar de `message`, `required_error` o `invalid_type_error`.
- `config.CASH_IN_MAX_AMOUNT` es `number` entero, por defecto 10000 (T2.4, campo `CASH_IN_MAX_AMOUNT` de `Config`). Design §8 define el body como factory `createCashInRequestSchema(maxAmount)`: el schema no importa una config cargada a nivel de módulo. La ruta de T4.7 la llama una vez al crear la app.
- `zValidator("header", ...)` recibe las claves de headers en minúscula: el campo es `"idempotency-key"`.
- T3.2 ya mapea el `HTTPException(400)` de Hono para un body que no es JSON. El hook solo ve fallos de zod.
- En el webhook, monto o moneda distintos a la operación no son un error de validación: son una anomalía que se registra y responde `200` (R9.9). El schema no debe rechazarlos.
- `.strict()` va solo en los bodies de nuestra API. El payload del webhook descarta campos desconocidos sin fallar (AGENTS.md, design §8): un campo nuevo del proveedor no debe provocar un `400` y reintentos infinitos.

## Pasos
1. `idempotencyKeySchema` exactamente como design §8: `z.uuid({ error: (issue) => issue.input === undefined ? "IDEMPOTENCY_KEY_MISSING" : "IDEMPOTENCY_KEY_INVALID" })`.
2. `cashInHeadersSchema = z.object({ "idempotency-key": idempotencyKeySchema })`, sin `.strict()`: el request trae otros headers.
3. `createCashInRequestSchema(maxAmount: number)` devuelve el schema de design §8 con `.max(maxAmount)` y `.strict()`:
   - `user_id`: `z.string().trim().min(1).max(64)`.
   - `amount`: `z.number().positive().max(maxAmount)` y el `refine` de 2 decimales sobre `String(v)` con `/^\d+(\.\d{1,2})?$/`, mensaje "Máximo 2 decimales".
   - `currency`: `z.literal("PEN", { error: "Solo se acepta PEN" })`.
   - `payment_method`: `z.string().trim().min(1).max(64)`.
4. `type CashInRequest = z.infer<ReturnType<typeof createCashInRequestSchema>>` y `type CashInHeaders = z.infer<typeof cashInHeadersSchema>`.
5. `webhookEventSchema`, con la forma de design §6:
   - `event_id`: string no vacío.
   - `type`: `z.enum(["charge.succeeded", "charge.failed", "charge.pending"])`.
   - `created_at`: `z.iso.datetime()`.
   - `data`: `charge_id` y `reference` string no vacío, `amount` `z.number()`, `currency` `z.string().length(3)`, `failure_code` `z.string().nullable()`.
   - Sin `.strict()` en el objeto raíz ni en `data`: `z.object` por defecto descarta las claves desconocidas, según AGENTS.md y design §8.
6. `src/shared/validation.ts`:
   - `issuesToFieldErrors(issues)`: `{ field: issue.path.join("."), message: issue.message }` por cada issue.
   - `validationHook`: si `!result.success`, lanza `new AppError("VALIDATION_ERROR", { detail, errors })`.
7. `idempotencyHeaderHook` en `cash-in.schemas.ts`: si `!result.success`, toma el `message` del issue de `idempotency-key` y lanza `AppError` con ese código (`IDEMPOTENCY_KEY_MISSING` o `IDEMPOTENCY_KEY_INVALID`) y `errors: []`.
8. Tests de schemas con `safeParse`:
   - Body válido pasa, con `amount` `100`, `100.5` y `100.55`.
   - `amount` `0`, `-1`, `100.555`, `"100"`, `maxAmount + 0.01` y `1e-7` fallan con `field: "amount"`.
   - `currency: "USD"` falla con "Solo se acepta PEN".
   - `user_id` y `payment_method` vacíos, solo espacios o de 65 caracteres fallan.
   - Un campo extra, por ejemplo `ammount`, falla por `.strict()`.
   - Header ausente da `IDEMPOTENCY_KEY_MISSING`; `"abc"` da `IDEMPOTENCY_KEY_INVALID`; `crypto.randomUUID()` pasa.
   - Webhook válido de design §6 pasa. `type` desconocido, `created_at` no ISO, `data.reference` faltante fallan. `currency: "USD"` y un `amount` distinto pasan el schema. Un campo extra en la raíz o en `data` pasa y no aparece en el resultado de `safeParse`.
9. Tests de hooks con `app.request()`, montando `correlation`, `zValidator("header", cashInHeadersSchema, idempotencyHeaderHook)`, luego `zValidator("json", createCashInRequestSchema(10000), validationHook)` y `app.onError(errorHandler)`:
   - Sin key y con body inválido responde `400 IDEMPOTENCY_KEY_MISSING`, no `VALIDATION_ERROR`.
   - Con key válida y body inválido responde `400 VALIDATION_ERROR` con `errors` por campo.
   - Con body `"{no json"` y `Content-Type: application/json` responde `400 VALIDATION_ERROR`.
   - El handler de la ruta no se ejecuta en ningún caso inválido.

## Restricciones
- Ningún schema importa `config` ni llama `loadConfig`.
- Los tipos se derivan con `z.infer`. No se duplican a mano.
- No agregar códigos de error. Solo `VALIDATION_ERROR`, `IDEMPOTENCY_KEY_MISSING` e `IDEMPOTENCY_KEY_INVALID`.
- Las rutas reales no se crean aquí.

## Trampas conocidas
- El agente tiende a escribir `import { config } from "../../infra/config"` dentro del schema. No existe una config exportada; el máximo entra por la factory `createCashInRequestSchema(maxAmount)` de design §8.
- El agente tiende a usar `z.coerce.number()` para `amount`. Acepta `"100"` y convierte `""` en `0`. El contrato pide número JSON.
- El agente tiende a validar decimales con `v.toFixed(2) === String(v)` o con `Number.isInteger(v * 100)`. El segundo falla con valores como `1.15`, porque `1.15 * 100` es `114.99999999999999`. Se usa el regex de design §8.
- El agente tiende a usar la API de zod 3: `z.string().uuid()`, `{ message }`, `required_error`, `errorMap`. Con zod 4 el mensaje del header no sale y se pierde la diferencia entre `MISSING` e `INVALID`.
- El agente tiende a escribir el header como `"Idempotency-Key"` en el schema. Hono entrega las claves en minúscula y el header siempre parecería ausente.
- El agente tiende a poner `.strict()` al schema de headers, que rechaza `content-type`, `user-agent` y el resto.
- El agente tiende a usar fixtures como `"11111111-1111-1111-1111-111111111111"`. `z.uuid()` de zod 4 valida versión y variante, y ese valor falla. Se usa `crypto.randomUUID()`.
- El agente tiende a restringir `currency` del webhook a `z.literal("PEN")` o a ponerle tope al `amount`. Un evento con moneda distinta respondería `400`, el proveedor lo reintentaría para siempre y nunca se registraría la anomalía de R9.9.
- El agente tiende a aplicar a `webhookEventSchema` la regla general de `.strict()`. El webhook es la excepción: un campo nuevo del proveedor daría `400` y el proveedor reintentaría para siempre.
- El agente tiende a usar `.passthrough()` o `z.looseObject` en el webhook. Eso conserva las claves desconocidas; se quiere el comportamiento por defecto de `z.object`, que las descarta.
- El agente tiende a devolver `c.json(...)` desde el hook en vez de lanzar `AppError`. El error no pasaría por el handler global y no sería problem+json.
- El agente tiende a llamar la factory en cada request dentro de la ruta. Se construye una vez al crear la app.

## Criterios de aceptación
- [ ] Cada regla de R1.4 tiene al menos un test que pasa y uno que falla.
- [ ] Un campo desconocido en el body de cash-in se rechaza. En el evento de webhook se descarta sin fallar.
- [ ] Header ausente da `IDEMPOTENCY_KEY_MISSING` y header no UUID da `IDEMPOTENCY_KEY_INVALID`.
- [ ] Sin key y con body inválido, gana el error de la key.
- [ ] Body no JSON y body inválido responden `400 VALIDATION_ERROR` en problem+json, con `errors` por campo cuando hay issues de zod.
- [ ] El schema del webhook acepta moneda y monto arbitrarios con la forma correcta.
- [ ] `grep -rn "infra/config" src/features/*/*.schemas.ts` no encuentra nada.
- [ ] `bun run test:unit` y `bun run typecheck` pasan.
