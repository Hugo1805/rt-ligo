## Objetivo
Funciones puras para firmar y verificar el header `X-Provider-Signature: t=<unix>,v1=<hex>`, donde `v1 = hex(HMAC_SHA256(secret, t + "." + rawBody))`. La verificación usa comparación en tiempo constante y rechaza timestamps fuera de tolerancia.

## Contexto
La ruta de T5.2 lee el body crudo con `c.req.text()`, llama a `verifyWebhookSignature` y, si falla, lanza `WEBHOOK_SIGNATURE_INVALID`. Recién después parsea y valida con zod.
La tolerancia viene de `config.WEBHOOK_TOLERANCE_S` (300 por defecto) y el secreto de `config.WEBHOOK_SECRET`. Este módulo no lee config: los recibe como parámetros.
`signWebhookPayload` se exporta para que los tests y `tools/mock-psp/` firmen igual que el verificador.

## Pasos
1. `signWebhookPayload({ secret, timestamp, rawBody }): string` devuelve el header completo `t=<timestamp>,v1=<hex>`. `timestamp` en segundos Unix.
2. `parseSignatureHeader(header): { t: number; v1: string } | null`:
   - Separa por `,` y cada parte por el primer `=`.
   - Exige exactamente un `t` entero positivo y un `v1` de 64 caracteres hex en minúscula.
   - Ante cualquier otra forma devuelve `null`. Nunca lanza.
3. `verifyWebhookSignature({ header, rawBody, secret, toleranceS, now }): boolean`:
   - `header: string | undefined`. Si falta o no parsea, `false`.
   - `now: () => number` en milisegundos, default `Date.now`.
   - Si `|floor(now() / 1000) - t| > toleranceS`, `false`.
   - Calcula el HMAC esperado con `createHmac("sha256", secret)` de `node:crypto` sobre `` `${t}.${rawBody}` `` en UTF-8.
   - Compara los dos digests como `Buffer` con `timingSafeEqual`, después de confirmar que tienen la misma longitud.
4. Tests:
   - Firmar y verificar el mismo body con el mismo secreto: `true`.
   - Body con un byte distinto, por ejemplo un espacio extra: `false`.
   - Otro secreto: `false`.
   - Timestamp 301 s en el pasado y 301 s en el futuro con tolerancia 300: `false`. A 300 s: `true`.
   - Header ausente, vacío, sin `v1`, sin `t`, con `t` no numérico, con `v1` de largo distinto o no hex: `false`, sin lanzar.
   - Un `v1` válido de otro timestamp con el `t` cambiado: `false`.
   - Un vector fijo: secreto, timestamp y body conocidos dan un header literal escrito en el test.

## Restricciones
- Funciones puras. Sin config, sin logger, sin estado de módulo.
- Sin dependencias nuevas: solo `node:crypto`.
- El HMAC se calcula sobre el string crudo recibido, nunca sobre un JSON re-serializado.

## Trampas conocidas
- El agente tiende a comparar con `===` o `!==`. Eso filtra por tiempo cuántos caracteres coinciden. Se usa `timingSafeEqual`.
- El agente tiende a llamar `timingSafeEqual` con buffers de distinto largo, que lanza `RangeError` y termina en un `500` en vez de un `401`. Se chequea el largo antes, o se valida el formato de `v1` al parsear.
- El agente tiende a firmar `JSON.stringify(JSON.parse(rawBody))`. Cambia espacios y orden, y la firma del proveedor real nunca coincide.
- El agente tiende a chequear solo timestamps viejos. Un `t` muy en el futuro también se rechaza, si no un atacante extiende la ventana de replay.
- El agente tiende a mezclar milisegundos y segundos: `t` está en segundos, `Date.now()` en milisegundos.
- El agente tiende a usar `Buffer.from(v1)` sin `"hex"` para uno de los lados, y compara bytes distintos.
- El agente tiende a lanzar `AppError` desde aquí. Este módulo devuelve `boolean`; el `AppError` lo lanza la ruta en T5.2.
- El agente tiende a loguear el secreto o el HMAC esperado para "depurar".

## Criterios de aceptación
- [ ] Un header generado con `signWebhookPayload` verifica `true` con el mismo body y secreto.
- [ ] Cambiar body, secreto o `t` hace que verifique `false`.
- [ ] Fuera de tolerancia, en el pasado o en el futuro, verifica `false`.
- [ ] Ningún header malformado hace lanzar a `verifyWebhookSignature`.
- [ ] El módulo usa `timingSafeEqual` y no compara digests con `===`.
- [ ] Los tests usan `now` inyectado y no dependen del reloj real.
- [ ] `bun run test:unit` y `bun run typecheck` pasan.
