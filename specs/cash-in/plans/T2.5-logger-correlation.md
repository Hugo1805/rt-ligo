## Objetivo
Logger pino en JSON y un middleware Hono que asigna un `request_id` a cada request, lo devuelve en la respuesta y lo deja en un child logger del contexto.

## Pasos
1. `createLogger` devuelve un logger pino con `base: { pod_id }` y timestamps ISO.
2. Declarar el tipo de variables de Hono: `requestId: string` y `logger: Logger`. Exportarlo para que las rutas lo usen.
3. Middleware `correlation(logger)`:
   1. Lee `X-Request-Id`.
   2. Lo acepta solo si cumple `^[A-Za-z0-9._-]{1,128}$`. Si no, genera `crypto.randomUUID()`.
   3. Guarda `requestId` y `logger.child({ request_id })` en el contexto.
   4. Setea `X-Request-Id` en la respuesta.
   5. Al terminar, loguea `{ event: "http.request", method, path, status, duration_ms }`.
4. Tests con una app Hono mínima creada en el propio test.

## Restricciones
- Sin `console.log`.
- No loguear headers completos ni bodies, porque pueden traer datos de tarjeta o firmas.

## Trampas conocidas
- El agente tiende a aceptar cualquier `X-Request-Id` entrante. Un valor arbitrario permite inyección en logs. Se valida el formato.
- El agente tiende a usar `AsyncLocalStorage` o un logger global mutable. Se usa el contexto de Hono.
- El agente tiende a loguear el body del request para "debug".

## Criterios de aceptación
- [ ] Sin header, la respuesta trae un `X-Request-Id` con formato UUID.
- [ ] Con un header válido, la respuesta devuelve el mismo valor.
- [ ] Con un header inválido, por ejemplo con saltos de línea o de 500 caracteres, se genera uno nuevo.
- [ ] Un handler puede leer `c.var.requestId` y `c.var.logger`.
