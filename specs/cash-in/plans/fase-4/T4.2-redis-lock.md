|---|---|

## Objetivo
Un lock genérico sobre Redis con `SET NX PX`, dueño identificado por UUID y liberación con Lua compare-and-delete. Si Redis falla, devuelve "sin lock" y loguea un warning, sin lanzar.

## Contexto
Es la capa 1 de design §2: una barrera rápida para el doble click. No es la garantía. La garantía es `@@unique([userId, idempotencyKey])` en PostgreSQL (T4.3). Por eso un fallo de Redis no debe tumbar el request: el servicio sigue sin lock y la DB decide.

El cliente Redis lo crea `createRedisClient(url)` de T2.6, con timeouts cortos para fallar rápido. Este módulo lo recibe inyectado.

El lock es genérico. La key `lock:cashin:{userId}:{key}` la arma el servicio de cash-in en T4.6, no este archivo.

## Pasos
1. Tipo de resultado, discriminado:

| Resultado | Significado |
|---|---|
| `{ status: "acquired", release }` | Este request es dueño del lock. `release()` lo libera. |
| `{ status: "busy" }` | Otro dueño tiene el lock. |
| `{ status: "unavailable" }` | Redis falló. Se sigue sin lock. |

2. `createRedisLock(redis)` devuelve `{ acquire(key, { ttlMs, logger }) }`.
3. `acquire`:
   1. `ownerId = crypto.randomUUID()`.
   2. `redis.set(key, ownerId, "PX", ttlMs, "NX")`. `"OK"` es `acquired`, `null` es `busy`.
   3. Si el comando lanza, `logger.warn({ event: "lock.unavailable", key, err })` y devuelve `unavailable`.
4. `release()` ejecuta con `redis.eval` el script:

```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1])
else
  return 0
end
```

   Si lanza, loguea warning y no propaga. El lock expira solo por TTL.
5. `release()` es idempotente: llamarlo dos veces no falla.
6. Tests de integración, cada uno con una key única `lock:test:${crypto.randomUUID()}`:
   - Dos `acquire` seguidos sobre la misma key: el primero `acquired`, el segundo `busy`.
   - Tras `release()`, un nuevo `acquire` obtiene el lock.
   - El lock expira solo: con `ttlMs` de 200 ms, tras esperar 300 ms se puede volver a tomar.
   - Un dueño cuyo lock expiró y fue tomado por otro llama `release()` y no borra el lock ajeno.
   - Con `Promise.all` de 10 `acquire` desde 3 clientes Redis distintos, exactamente uno queda `acquired`.
   - Redis caído: un cliente apuntando a un puerto sin servidor, por ejemplo `redis://localhost:6399`, devuelve `unavailable` en menos de 1 s, no lanza y loguea warning.

## Restricciones
- `src/infra/lock.ts` no conoce cash-in ni importa de `src/features/`.
- El logger se recibe por parámetro. Nada de `console.log`.
- `ttlMs` lo pasa quien llama. En cash-in viene de `config.LOCK_TTL_MS`, 15000 por defecto (design §2, §13). Este módulo no tiene un TTL por defecto propio.
- Sin dependencias nuevas. Nada de `redlock`.

## Trampas conocidas
- El agente tiende a liberar con un `DEL` directo. Un pod cuyo lock expiró borraría el lock de otro. La liberación es compare-and-delete en Lua.
- El agente tiende a hacer `GET` y luego `DEL` desde TypeScript. No es atómico. Tiene que ser el script.
- El agente tiende a usar `SETNX` seguido de `EXPIRE`. Si el proceso muere entre ambos, el lock queda eterno. Es un solo `SET ... NX PX`.
- El agente tiende a dejar que la excepción de ioredis suba. Con Redis caído el request debe seguir: se devuelve `unavailable`.
- Con Redis caído, ioredis encola comandos en su offline queue y el `acquire` se cuelga. Si el test de Redis caído tarda más de 1 s, revisar las opciones de `createRedisClient` de T2.6 (`enableOfflineQueue`, `maxRetriesPerRequest`, `commandTimeout`) y reportarlo antes de parchear aquí.
- El agente tiende a fijar un TTL literal como `30000` en el código. El TTL es `config.LOCK_TTL_MS` (15000 por defecto) y entra por parámetro.
- El agente tiende a usar un `ownerId` fijo por proceso. Debe ser uno por `acquire`.
- El agente tiende a dejar clientes Redis abiertos al final del test y `bun test` no termina. Cerrar con `quit()` o `disconnect()` en `afterAll`.

## Criterios de aceptación
- [ ] `acquire` usa un único `SET key owner PX ttl NX`.
- [ ] `release` usa el script Lua de compare-and-delete.
- [ ] Un `release` tardío no borra el lock de otro dueño.
- [ ] Con 10 intentos concurrentes desde 3 clientes, solo uno obtiene el lock.
- [ ] Con Redis caído, `acquire` devuelve `unavailable` en menos de 1 s y se registra un warning.
- [ ] Cada test usa una key única y cierra sus clientes.
