## Objetivo
`applyCredit`, la única función que acredita saldo: en una sola transacción lleva la operación a `COMPLETED`, incrementa el saldo y crea el asiento con `balanceAfter`. Si la operación ya es terminal, es un no-op.

## Contexto
Es la pieza más crítica del repo: aquí se evita el doble abono. La usan el flujo síncrono (T4.6), el webhook (T5.1) y el reconciliador (T6.1). El webhook la ejecuta dentro de su propia transacción, junto con el insert del evento (design §6), por eso acepta un cliente de transacción opcional.

Tres defensas, en este orden:
1. CAS con `updateMany` desde `PROCESSING` o `UNKNOWN`. Solo un actor obtiene `count = 1`.
2. `balance: { increment }`: una sola sentencia `balance = balance + x`. El `UPDATE` toma el lock de fila de la wallet hasta el commit, así dos abonos del mismo usuario se serializan y `balanceAfter` es exacto.
3. `LedgerEntry.operationId @unique`: aunque falle todo lo anterior, un segundo asiento rompe la transacción.

`new_balance` de la respuesta sale de `LedgerEntry.balanceAfter` (design §5), por eso es igual en cada replay.

El servicio de cash-in (T4.6) también necesita leer la wallet para validar existencia y moneda (design §3). `wallet.service.ts` expone `applyCredit` y `getWallet`, porque una feature solo importa de otra a través de su `<feature>.service.ts` (AGENTS.md, design §5). `getWallet` es la única forma en que cash-in lee una wallet.

Los estados de origen del CAS salen de `allowedSources("COMPLETED")` de `src/shared/operation-state-machine.ts` (T3.1).

## Pasos
1. `applyCredit({ operationId, providerChargeId, actor }, tx?)`, con `actor: "api" | "webhook" | "reconciler"`, devuelve `{ applied, from, balanceAfter }`:

| Resultado | Cuándo |
|---|---|
| `{ applied: true, from, balanceAfter }` | Esta llamada acreditó. `from` es `PROCESSING` o `UNKNOWN`. |
| `{ applied: false, from, balanceAfter }` | La operación ya era terminal o no estaba en un estado acreditable. `from` es el estado leído; `balanceAfter` es el del asiento existente si la operación ya está `COMPLETED`, o `null`. |

2. Cuerpo, ejecutado sobre `tx` si viene, o dentro de `prisma.$transaction(async (tx) => ...)` si no:
   1. Leer la operación por `id` dentro de la transacción con `select: { userId, amount, status }` y el `balanceAfter` de su asiento. `userId` y `amount` salen de aquí, nunca del llamador. Si no existe, lanzar error (es un bug del llamador).
   2. CAS: `tx.cashInOperation.updateMany({ where: { id, status: { in: allowedSources("COMPLETED") } }, data: { status: "COMPLETED", providerChargeId, completedAt: new Date() } })`.
   3. Si `count === 0`, devolver `{ applied: false, from: status leído, balanceAfter }`. Nada más se toca.
   4. `tx.wallet.update({ where: { userId }, data: { balance: { increment: amount } } })`.
   5. `tx.ledgerEntry.create({ data: { walletId, operationId, type: "CREDIT", amount, balanceAfter: wallet.balance } })`.
   6. Devolver `{ applied: true, from: status leído, balanceAfter: wallet.balance }`.
3. `applyCredit` no loguea: no tiene el logger del request y, con `tx` externo, un rollback posterior haría mentir al log. Devuelve `from` y el llamador registra `operation.transition` después del commit con el mismo `actor` que pasó.
4. `getWallet(userId)` devuelve `{ id, userId, currency, balance } | null`.
5. Tests de integración, cada uno con wallet y operaciones propias creadas con `tests/helpers/factories.ts`:
   - Operación `PROCESSING` de 100.00 sobre wallet en 250.00: `applied: true`, `balanceAfter` 350.00, estado `COMPLETED`, `providerChargeId` y `completedAt` guardados, un asiento.
   - Desde `UNKNOWN` también acredita.
   - Segunda llamada sobre la misma operación: `applied: false`, `from: "COMPLETED"`, `balanceAfter` igual al de la primera, saldo sin cambio, un solo asiento.
   - Desde `FAILED` o `PENDING`: `applied: false` y saldo sin cambio.
   - Misma operación, `Promise.all` de 10 `applyCredit` desde 3 clientes Prisma distintos: exactamente un `applied: true`, un asiento y el saldo sube una sola vez.
   - Misma wallet, 50 operaciones distintas con montos como 10.01, 0.10 y 99.99, `Promise.all` desde 3 clientes Prisma: saldo final igual a la suma exacta calculada con `Prisma.Decimal`, 50 asientos, y los `balanceAfter` son todos distintos y el mayor es el saldo final.
   - Con `tx` externo que lanza después de `applyCredit`: no queda ni el `COMPLETED`, ni el abono, ni el asiento.

## Restricciones
- Las tres escrituras van en la misma transacción. Sin excepciones.
- Saldo solo con `{ increment }`. Prohibido leer `balance` para calcular el nuevo.
- Montos y comparaciones con `Prisma.Decimal`. En los tests, comparar con `.equals()` o `.toFixed(2)`, nunca con `number`.
- Solo cliente Prisma. Prohibido `$queryRaw` y `$executeRaw`.
- `wallet` no importa de `features/cash-in/`. Los estados de origen salen de `allowedSources("COMPLETED")` de `src/shared/operation-state-machine.ts`.
- Si `applyCredit` recibe `tx`, no abre otra transacción.

## Trampas conocidas
- El agente casi siempre lee la wallet, suma en TypeScript y hace `update({ balance: nuevo })`. Es la race condition de R8. Solo `increment`.
- El agente tiende a crear el asiento antes del CAS o fuera de la transacción. Si el CAS da 0, ya se escribió un asiento o un saldo.
- El agente tiende a hacer el CAS con `update` y `where: { id, status }`. Si el estado ya cambió, `update` lanza `P2025` en lugar de devolver `count = 0`, y el no-op idempotente se vuelve una excepción. Es `updateMany`.
- El agente tiende a tratar `count === 0` como error y lanzar. Es un no-op idempotente: otro actor ya acreditó o la operación terminó.
- El agente tiende a calcular `balanceAfter` como `saldoLeído + amount`. Sale del resultado del `update` con `increment`.
- El agente tiende a abrir `prisma.$transaction` aunque reciba `tx`. Un `$transaction` anidado no existe en Prisma: el webhook perdería la atomicidad con su evento.
- El agente tiende a importar algo de `features/cash-in/` desde `wallet`. Viola la regla de dependencias entre features. La máquina de estados está en `src/shared/`.
- El agente tiende a recibir `userId` o `amount` como parámetros de `applyCredit`. Se leen de la operación dentro de la transacción, para que un llamador no pueda acreditar un monto distinto al de la operación.
- El agente tiende a escribir el test de concurrencia con un solo cliente Prisma y `for` secuencial. Se usa `Promise.all` con varios clientes.
- El agente tiende a loguear la transición dentro de la transacción. Si luego hace rollback, el log miente. El log lo emite el llamador tras el commit.
- Orden de locks: la transacción toca primero la fila de la operación y luego la de la wallet. No invertirlo en ningún llamador, para no abrir deadlocks.

## Criterios de aceptación
- [x] CAS, `increment` y asiento ocurren en una sola transacción.
- [x] 10 llamadas concurrentes sobre la misma operación producen un abono y un asiento.
- [x] 50 abonos concurrentes de la misma wallet dan la suma exacta en `Decimal`.
- [x] `balanceAfter` sale del `update` con `increment`.
- [x] Con `tx` externo, un rollback posterior deshace todo.
- [x] `applyCredit` no abre transacción si recibe `tx`.
- [x] La firma es `applyCredit({ operationId, providerChargeId, actor }, tx?)` y devuelve `{ applied, from, balanceAfter }`.
- [x] `userId` y `amount` se leen de la operación dentro de la transacción.
- [x] `wallet` no importa de `features/cash-in/`.
- [x] Cada test usa datos únicos y cierra sus clientes.
- [x] `grep -r "queryRaw\|executeRaw" src` no encuentra nada.

## Notas de revisión
- Implementado por Claude Code, según la asignación del plan.
- Desvío deliberado del paso 2.3: si el CAS da `count = 0`, se relee la operación dentro de la misma transacción antes de devolver. Con el `from` leído antes del CAS, un perdedor concurrente devolvía `PROCESSING` y `balanceAfter: null` aunque la operación ya estaba `COMPLETED`. El `updateMany` del perdedor espera el lock de fila hasta el commit del ganador, así que la relectura en READ COMMITTED ve el estado real y su asiento. El test de 10 llamadas concurrentes lo verifica.
- Verificado con una prueba de mutación: cambiar `increment` por leer y escribir el saldo hace fallar el test de 50 abonos concurrentes.
- Los tests usan `providerChargeId` aleatorios: la columna es `@unique` y los datos persisten entre corridas. Se corrió la suite tres veces seguidas.
