## Objetivo
Un proveedor de pagos falso como servicio HTTP aparte, idempotente por `reference`, y el adaptador `HttpPaymentProvider` que implementa el puerto `PaymentProvider` de T4.1 hablando con él. `server.ts` elige el adaptador según `PROVIDER_MODE`.

## Contexto
El `mock-psp` es un contenedor propio a propósito (design §1, ai-log #6): si viviera en la memoria de cada pod de la app, dos réplicas no compartirían cobros y la idempotencia por referencia no se podría probar entre pods. Por eso puede guardar los cobros en su propia memoria: es un único proceso compartido por todos los pods. Reiniciarlo pierde los cobros, y eso es aceptable en e2e.

El contrato HTTP del `mock-psp` está en design §11. Se copia aquí, más `GET /health` para Compose:

| Método y ruta | Respuesta |
|---|---|
| `POST /charges` con `{ reference, amount, currency, payment_method }` | `200 { status: "succeeded", charge_id }` o `200 { status: "declined", charge_id, failure_code }` |
| `GET /charges/:reference` | `200` con el mismo cuerpo, o `404` si no conoce la referencia |
| `GET /__admin/charges/:reference` | `200 { charge, attempts }`: el cargo y cuántas veces se llamó `POST /charges` con esa referencia. Solo para e2e. |
| `GET /health` | `200` |

Un rechazo es un resultado de negocio: va como `200` con `status: "declined"`, no como un 4xx.

Escenarios por `payment_method`, de design §11:

| `payment_method` | Comportamiento |
|---|---|
| `card_ok` o cualquier otro | Registra el cargo `succeeded` y responde. |
| `card_declined` | Registra el cargo `declined` con `insufficient_funds`. |
| `card_timeout` | Registra el cargo `succeeded`, espera `MOCK_PSP_TIMEOUT_DELAY_MS` (mayor que `PROVIDER_TIMEOUT_MS`) antes de responder, y luego envía un `charge.succeeded` firmado a `MOCK_PSP_WEBHOOK_URL`. |
| `card_flaky` | La primera llamada con esa referencia responde `503` sin registrar el cargo. La siguiente cobra. El fallo es por referencia, no global. |

Errores del puerto, de design §11. Ninguno lleva `code` de `AppError`:

| Error del adaptador | Cuándo | Acción del servicio |
|---|---|---|
| `ProviderTimeoutError` | Sin respuesta dentro de `PROVIDER_TIMEOUT_MS`. | `UNKNOWN` sin reintento en línea. |
| `ProviderUnavailableError` | Error de conexión o `5xx`. | Reintento técnico con la misma referencia. |
| `ProviderUnexpectedError` | `4xx` inesperado o cuerpo que no valida con zod. | `UNKNOWN` sin reintento. Nunca `FAILED` sin certeza. |

## Pasos
1. `mock-psp`: un `Map<reference, Charge>` y un `Map<reference, attempts>` dentro del proceso del mock. `POST /charges` con una referencia ya conocida devuelve el cargo existente, sin crear otro ni cambiar su resultado, aunque cambie el `payment_method`.
2. Validar el body de `POST /charges` con zod. Un body inválido responde `400`.
3. `card_timeout`: el cargo queda registrado antes de la espera, así `GET /charges/:reference` ya responde `succeeded` y el reconciliador lo puede resolver aunque el webhook no llegue. El webhook se envía tras `MOCK_PSP_WEBHOOK_DELAY_MS` con `event_id` nuevo, `type: "charge.succeeded"` y `data` según design §6, con `amount` como número.
4. `webhook-sender`: firma `HMAC_SHA256(WEBHOOK_SECRET, t + "." + rawBody)` en hex y la envía en `X-Provider-Signature`. Si la respuesta no es 2xx, reintenta hasta 3 veces con el mismo `event_id` y el mismo body.
5. `HttpPaymentProvider(baseUrl, timeoutMs, logger)`:
   - `charge(input)`: `POST {baseUrl}/charges` con `signal: AbortSignal.timeout(timeoutMs)` y header `X-Request-Id: input.requestId`.
   - `getCharge(reference)`: `GET {baseUrl}/charges/:reference`. `404` devuelve `{ status: "not_found" }`.
   - El cuerpo de cada respuesta se valida con zod antes de devolverlo.
6. Mapeo de errores:
   - Aborto por timeout (`TimeoutError`): `ProviderTimeoutError`.
   - Error de red o conexión rechazada: `ProviderUnavailableError`.
   - `5xx`: `ProviderUnavailableError`.
   - `4xx` inesperado (cualquiera salvo el `404` de `getCharge`) o cuerpo que no pasa el schema zod: `ProviderUnexpectedError`.
   - El mensaje del error es fijo. El detalle crudo (status, body, `cause`) solo va al log.
7. `server.ts`: `PROVIDER_MODE=http` construye `HttpPaymentProvider` con `PROVIDER_BASE_URL` y `PROVIDER_TIMEOUT_MS`. `fake` sigue usando `FakePaymentProvider`.

## Restricciones
- El adaptador no reintenta. Los reintentos técnicos ya los hace el servicio con `src/shared/retry.ts` (T3.4, T4.6) y `PROVIDER_MAX_RETRIES`.
- El adaptador nunca genera ni cambia la referencia: envía la que recibe.
- Sin dependencias nuevas: `fetch` y `AbortSignal.timeout` son nativos de Bun, Hono y zod ya están.
- El mock no importa nada de `src/features/`. Tiene su propia firma, así un error de firma en la app se detecta en e2e.
- Prohibido `console.log` en el adaptador. En el mock se usa pino.

## Trampas conocidas
- Guardar los cobros del proveedor falso en memoria de cada pod de la app, por ejemplo usando `FakePaymentProvider` detrás de `PROVIDER_MODE=http`. Rompe justo lo que el e2e quiere probar.
- Reintentar en el adaptador un timeout o un 5xx. Con el retry del servicio se multiplican los intentos, y reintentar un timeout en línea viola design §7.
- Responder el rechazo con `402` u otro 4xx. Un rechazo va como `200` con `status: "declined"` (design §11). Si el mock responde 4xx, el adaptador lo mapea a `ProviderUnexpectedError` y la operación queda `UNKNOWN` en vez de `FAILED`.
- Mapear un 4xx inesperado o un cuerpo inválido a `ProviderUnavailableError`. El servicio lo reintentaría como si fuera un fallo técnico. Va como `ProviderUnexpectedError`, sin reintento.
- Mapear un 4xx inesperado a un `declined`. Sería marcar `FAILED` sin certeza de que el cobro no salió.
- Usar `setTimeout` + `AbortController` sin limpiar el timer, o un `Promise.race` que deja la petición viva. Usar `AbortSignal.timeout`.
- Distinguir mal el aborto: `AbortSignal.timeout` lanza un `DOMException` con `name === "TimeoutError"`, no `AbortError`.
- Propagar `err.message` del fetch o el body del mock en el error. R12.3 lo prohíbe y el error handler podría terminar exponiéndolo.
- `card_flaky` que falla "la primera vez" de forma global en vez de por referencia. Con dos tests en paralelo, uno nunca ve el 503.
- `card_timeout` que no registra el cargo antes de esperar. Entonces el reconciliador recibe `not_found` y reenvía el cobro, y el caso deja de probar lo que debe.
- Firmar un JSON distinto al que se envía, por ejemplo firmar el objeto y enviar otro `JSON.stringify`. Firmar y enviar el mismo string.

## Criterios de aceptación
- [x] Dos `POST /charges` con la misma referencia devuelven el mismo `charge_id`, y `attempts` vale 2.
- [x] `card_declined` responde `200` con `status: "declined"` y `failure_code: "insufficient_funds"`.
- [x] `card_flaky` responde `503` la primera vez y `succeeded` la segunda, con la misma referencia.
- [x] `card_timeout` hace que `HttpPaymentProvider.charge` lance `ProviderTimeoutError`, y luego `getCharge` devuelve `succeeded`.
- [x] El webhook de `card_timeout` lleva una firma que verifica con el secreto configurado.
- [x] Un `503` y una conexión rechazada lanzan `ProviderUnavailableError` con mensaje fijo.
- [x] Un `4xx` inesperado y un cuerpo `200` que no pasa el schema lanzan `ProviderUnexpectedError` con mensaje fijo.
- [x] El request al mock lleva el `X-Request-Id` recibido.
- [x] `getCharge` de una referencia desconocida devuelve `{ status: "not_found" }`.
- [x] `grep -rn "retry\|withRetry" src/infra/payment-provider/http.provider.ts` no encuentra lógica de reintento.
- [x] `bun run typecheck` pasa.
