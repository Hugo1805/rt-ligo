## Objetivo
Una función pura que valida las variables de entorno con zod y devuelve una config tipada. Si falta una variable, el proceso no levanta.

## Archivos
| Acción | Ruta | Contenido |
|---|---|---|
| crear | `src/infra/config.ts` | Schema zod, tipo `Config` y `loadConfig(env)`. |
| crear | `src/infra/config.unit.test.ts` | Tests unitarios. |

## Pasos
1. Schema zod con todas las variables de design §13, más `NODE_ENV`, `PORT` con default 3000, `LOG_LEVEL` con default `info` y `POD_ID` con default el hostname.
2. Los numéricos usan `z.coerce.number().int().positive()` con su default.
3. `PROVIDER_BASE_URL` es obligatoria solo si `PROVIDER_MODE` es `http`. Usar un refinamiento.
4. `loadConfig(env: Record<string, string | undefined> = process.env): Config`. Lanza un error que lista todas las variables inválidas.
5. Exportar `type Config = z.infer<typeof configSchema>`.

## Restricciones
- `loadConfig` no lee `process.env` por dentro si recibe `env`. Así se testea sin tocar el entorno global.
- No exportar una config ya cargada a nivel de módulo. La carga ocurre en `server.ts`.
- El error no debe imprimir valores de secretos como `WEBHOOK_SECRET` o la clave de `DATABASE_URL`.

## Trampas conocidas
- El agente tiende a exportar `export const config = loadConfig()`, que rompe los tests y obliga a tener env en cada import.
- El agente tiende a imprimir el `env` completo al fallar, filtrando secretos.

## Criterios de aceptación
- [ ] Con un env completo, devuelve la config con los tipos correctos y los defaults aplicados.
- [ ] Sin `DATABASE_URL`, lanza un error que la nombra.
- [ ] Con `PROVIDER_MODE=http` y sin `PROVIDER_BASE_URL`, lanza un error.
- [ ] Un `PROVIDER_TIMEOUT_MS` no numérico lanza un error.
- [ ] El mensaje de error no contiene el valor de `WEBHOOK_SECRET`.
